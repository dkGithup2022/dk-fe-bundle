# 페이지 API 스펙

> 산출물(`docs/`, `src/` 아래 파일)은 플러그인 폴더가 아니라 **현재 작업 중인 프로젝트** 아래에 만든다. 스킬 본문의 경로는 모두 그 프로젝트 기준이다.

## 에이전틱 동작

이 동작은 에이전틱한 동작입니다. 아래 순서에 맞게 실행하되, 수행 계획과 종료 조건을 고려하여 여러 번 수행해 결과를 도출해도 됩니다.

### 목적

페이지 하나에 관여하는 API 목록을 빠짐없이 뽑아, 각각의 목적 · 동작 · HTTP 요청 스펙을 사람이 검사할 수 있게 남기는 것이 목적입니다. 이 문서가 페이지 제작과 BE 협의의 근거가 됩니다. 코드 파일은 만들지 않습니다.

### 입력 & 출력

입력:
- 페이지 디자인. 그 페이지에 속하는 화면 이미지 파일들. 인자로 받거나 대화에서 추론한다.
- `docs/pages/{라우트 이름}/data.md` (fe-page-data 산출물). "API 데이터" 절이 요청 · 응답 모양의 출발점이다.
- `docs/pages/{라우트 이름}/components.md` (fe-page-components 산출물). 컴포넌트의 콜백이 곧 동작이다.
- BE API 스펙 (있으면). 있으면 경로 · 메서드 · 필드명은 BE 를 따른다.
- 이미 있는 API: `src/types/api/`, `src/lib/api/mock/handlers.ts` 의 경로, `src/lib/*-api.ts` 의 함수.
- 기존 코드가 있으면 그 라우트 폴더.
- 대화에서 사용자가 정한 사항.

출력:
- `docs/pages/{라우트 이름}/api.md`. 아래 형식.

```markdown
# {라우트 이름} API

라우트: /{route}
화면: {파일명}, {파일명}
입력: docs/pages/{라우트 이름}/data.md, docs/pages/{라우트 이름}/components.md
작성: {날짜}
상태: 검수 대기. 사용자가 보고 고친 뒤 "검수 완료" 로 바꾸면 fe-generate-api 를 실행한다.

## 목록

이 페이지에 관여하는 것 전부. 종류는 셋 중 하나.

| # | 종류 | 이름 | 트리거 | 상태 |
|---|---|---|---|---|
| 1 | 도메인 CRUD | {도메인} 목록 읽기 | 진입 · 탭 · 검색 | 있음 (lib/{domain}-api.ts {함수}) / 새로 필요 |
| 2 | 페이지 동작 | {정렬 바꾸기} | {버튼} | API 아님 |
| 3 | 유즈케이스 | {팔로우 토글} | {버튼} | 새로 필요 |

## 1. 도메인 CRUD

한 도메인의 목록 · 단건 · 생성 · 수정 · 삭제. 리소스 경로 하나로 표현되는 것.

### {메서드} {경로} — {이름}
- 목적: {무엇을 위해}
- 동작: {요청하면 무슨 일이 일어나는지 한두 줄}
- 인증: 필요 / 불필요
- 상태: 있음 ({함수}) / 새로 필요

요청

| 위치 | 이름 | 타입 | 필수 | 뜻 · 근거 |
|---|---|---|---|---|
| query | {name} | {타입} | 아니오 | {파일명} "{화면 문구}" |

응답 `{Name}Response` (data.md 의 API 데이터 이름)

| 필드 | 타입 | 뜻 · 화면 어디에 |
|---|---|---|
| {field} | {타입} | {파일명} {영역} |

## 2. 페이지 안 동작

서버를 부르지 않는 동작. API 는 아니지만 빠뜨리지 않으려고 기록한다.

| 이름 | 트리거 | 무엇이 바뀌는지 | 나중에 API 가 될 수 있는가 |
|---|---|---|---|
| {정렬 바꾸기} | {버튼} | {상태 sort} | {값이 늘면 서버 정렬 파라미터} |

## 3. 유즈케이스

특정 비즈니스 목적이나 흐름이 있는 것. 한 리소스의 CRUD 로 설명되지 않는다. 팔로우 · 참석 신청 · 발행 · 정기 등록처럼 여러 도메인을 건드리거나 상태 전이가 있는 것.

### {메서드} {경로} — {이름}
- 목적: {비즈니스 목적}
- 동작: {흐름. 어떤 도메인이 어떻게 바뀌는지}
- 인증: 필요 / 불필요
- 상태: 있음 / 새로 필요

요청

| 위치 | 이름 | 타입 | 필수 | 뜻 · 근거 |
|---|---|---|---|---|

응답 `{Name}Response`

| 필드 | 타입 | 뜻 · 화면 어디에 |
|---|---|---|

## 결정 필요

| 항목 | 후보 | 이유 |
|---|---|---|
```

### 분류 규칙

동작 하나를 놓고 순서대로 묻는다.

1. 서버를 부르지 않는가? (탭 · 정렬 · 필터 선택, 입력 중인 값, 시트 열고 닫기)
   → 페이지 안 동작. 나중에 API 가 될 수 있으면 그렇게 적는다.
2. 한 도메인의 목록 · 단건 · 생성 · 수정 · 삭제로 설명되는가?
   → 도메인 CRUD. 경로는 `/api/{resources}`, `/api/{resources}/{id}`.
3. 그 밖에 비즈니스 목적이나 흐름이 있는가? (관계를 만들거나 끊음, 상태 전이, 여러 도메인을 한 번에 바꿈, 계산 결과를 내려줌)
   → 유즈케이스. 경로는 `/api/{resources}/{id}/{action}` 또는 `/api/{usecase}`.
4. 가르기 어려우면 "결정 필요" 에 올린다.

정리 규칙:

1. 도메인에 대한 CRUD 로 해결되는 경우라면 그렇게 한다. 예: 특정 아티클이 종료되었는지는 아티클 조회로 판단한다. 별도 API 를 만들지 않는다.
2. 이미 있는 API 목록에 있는지 파악한다. 있으면 재사용한다. 애매한 것은 AskUser 로 묻는다.
3. 인증은 "필요 / 불필요" 표시만 한다. 구현은 이 스킬의 일이 아니다.

### 권장 동작 순서

1. 화면과 문서 읽기
   화면 이미지를 보고 서버가 필요한 순간과 필요 없는 동작을 전부 적는다. `data.md` 의 API 데이터, `components.md` 의 콜백 props 를 읽는다.

2. 있는 API 읽기
   `src/lib/api/mock/handlers.ts` 의 경로와 `src/lib/*-api.ts` 의 함수를 뽑는다.

3. 목록 만들기
   동작마다 종류 · 트리거 · 상태를 적는다. 분류 규칙을 따른다.

4. 절 쓰기
   도메인 CRUD 와 유즈케이스는 엔드포인트마다 목적 · 동작 · 인증 · 상태 · 요청 · 응답을 적는다. 페이지 안 동작은 표 한 줄.

5. 사용자 확인
   "새로 필요" 와 "결정 필요" 를 AskUser 로 하나씩 묻는다. 정해진 것은 반영하고, 정하지 않은 것은 그대로 둔다.

6. 파일 쓰기
   `docs/pages/{라우트 이름}/api.md` 로 쓴다. 상태는 "검수 대기".

7. 검수 요청
   문서 전체를 사용자에게 보여주고 멈춘다. 다음 단계(fe-generate-api)는 사용자가 상태를 "검수 완료" 로 바꾼 뒤에만 시작한다.

### 종료 조건

- [ ] 화면의 모든 동작이 "목록" 에 있고 세 종류 중 하나로 분류되어 있다
- [ ] 도메인 CRUD 와 유즈케이스마다 목적 · 동작 · 인증 · 상태 · 요청 · 응답이 있다
- [ ] `docs/pages/{라우트 이름}/api.md` 가 "검수 대기" 상태로 저장되었고 사용자에게 보여주었다

아래 상황이면 AskUser 로 상황을 브리핑하고 정보를 구하세요.
- 새로 필요한 엔드포인트가 있다
- 있는 엔드포인트의 응답이 화면에 모자란다
- 도메인 CRUD 인지 유즈케이스인지 가르기 어렵다
- BE 스펙과 화면 동작이 다르다
- 동작의 결과가 화면에 없다 (제출 후 어디로 가는지, 무엇이 바뀌는지 알 수 없다)
