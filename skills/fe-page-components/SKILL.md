# 페이지 컴포넌트 정리

> 산출물(`docs/`, `src/` 아래 파일)은 플러그인 폴더가 아니라 **현재 작업 중인 프로젝트** 아래에 만든다. 스킬 본문의 경로는 모두 그 프로젝트 기준이다.

## 에이전틱 동작

이 동작은 에이전틱한 동작입니다. 아래 순서에 맞게 실행하되, 수행 계획과 종료 조건을 고려하여 여러 번 수행해 결과를 도출해도 됩니다.

### 목적

페이지 하나를 어떤 컴포넌트로 조립할지 정하는 것이 목적입니다. 있는 공용 컴포넌트를 쓸 수 있는 곳, 새로 만들어야 하는 곳, 공용으로 올려야 하는 곳을 가른 뒤 핸드오프 문서로 남깁니다. 코드 파일은 만들지 않습니다.

### 입력 & 출력

입력:
- 페이지 디자인. 그 페이지에 속하는 화면 이미지 파일들. 인자로 받거나 대화에서 추론한다.
- `src/components/ui/`, `src/components/layout/`, `src/components/{domain}/` 에 있는 컴포넌트와 그 `.types.ts`.
- `docs/pages/{라우트 이름}/data.md` (있으면). 새 컴포넌트의 props 에 어떤 데이터가 들어가는지 여기서 가져온다.
- 기존 코드가 있으면 그 라우트 폴더.
- 대화에서 사용자가 정한 사항.

출력:
- `docs/pages/{라우트 이름}/components.md`. 아래 형식.

```markdown
# {라우트 이름} 컴포넌트

라우트: /{route}
화면: {파일명}, {파일명}
작성: {날짜}
상태: 사용자 검수 전. 이 파일을 고친 뒤 다음 스킬이 파일을 만든다.

## 영역

- A {영역 이름}: {보이는 것}
- B {영역 이름}: {보이는 것}

## 공용 컴포넌트 사용

| 영역 | 컴포넌트 | 쓰는 props | 비고 |
|---|---|---|---|
| A | ui/{Name} | {prop}={값 출처} | 그대로 사용 |
| B | ui/{Name} | {prop} | {디자인과 다른 점. 사용자 결정 필요} |

## 추가 컴포넌트

반복되거나, 비즈니스 · 구조적 의미가 있는 덩어리.

| 이름 | 위치 | props | 안에 쓰는 공용 컴포넌트 | 근거 |
|---|---|---|---|---|
| {Name} | src/components/{domain}/{Name}.tsx | {prop}: {타입} | ui/{Name}, ui/{Name} | {파일명} {영역}. {왜 컴포넌트인지} |

## 공용 승격 후보 (사용자 판단 필요)

다른 페이지에서도 쓰일 가능성이 높은 것. 예: 헤더, 푸터.

| 이름 | 지금 위치 | 올릴 위치 | 이유 |
|---|---|---|---|
| {Name} | src/components/{domain}/ | src/components/ui/ 또는 layout/ | {다른 페이지 어디에서 쓰일지} |

## 기존 컴포넌트 수정 필요 (사용자 판단 필요)

| 컴포넌트 | 디자인과 다른 점 | 후보 |
|---|---|---|
| ui/{Name} | {무엇이 다른지} | prop 추가 / 페이지에서 감싸서 해결 / 디자인에 맞추지 않음 |
```

### 판단 규칙

공용 컴포넌트 사용:
- 화면의 요소가 `components/ui/` 의 컴포넌트와 같은 역할이면 그것을 쓴다. 색 · 크기 · 문구 차이는 props 로 해결되면 "그대로 사용".
- props 로 해결이 안 되는 차이(모양 · 동작이 다름)는 "기존 컴포넌트 수정 필요" 에 올리고 AskUser 로 묻는다. 후보는 셋이다. 공용 컴포넌트에 prop 을 더한다 / 페이지 쪽에서 감싸서 해결한다 / 디자인을 공용에 맞춘다.

추가 컴포넌트:
- 같은 모양이 화면 안에서 반복되거나 다른 화면에서도 나올 가능성이 있는 것.
- 비즈니스 · 구조적 의미가 있는 덩어리. 예: 아티클 카드, 모임 한 줄, 댓글 한 개.
- 위치는 `components/{domain}/`. props 는 `data.md` 의 도메인 · API 데이터 타입을 받아도 된다 (`ui/` 와 달리 도메인 타입 허용).
- 한 번만 나오고 의미 단위도 아닌 것(제목 한 줄, 여백, 구분선)은 컴포넌트로 만들지 않는다. 페이지 본문에 둔다.

크기:
- 전체 컨테이너와 각 하위 컴포넌트와 구성 요소는 고정 크기보다는 flex 를 사용하는 것이 권장됩니다.
- 크기를 직접 선언해야 한다면 숫자를 넣기 보다는 tailwind 변수에 제안된 크기 숫자가 있는지 확인하세요.

공용 승격:
- 다른 페이지에서 쓰일 가능성이 높은 것은 후보로 올린다. 예: 헤더, 푸터. 올릴지는 AskUser 로 묻는다. 스킬이 스스로 올리지 않는다.

### 권장 동작 순서

1. 화면 읽기
   페이지의 화면 이미지를 전부 본다. 화면을 영역으로 나누고 영역마다 보이는 요소를 적는다. 기존 코드가 있으면 이미 쓰는 컴포넌트를 적는다.

2. 있는 컴포넌트 읽기
   `src/components/` 의 컴포넌트 이름과 props 를 뽑는다.

3. 영역마다 대응
   요소 하나하나를 공용 컴포넌트에 대응한다. 대응되면 "공용 컴포넌트 사용" 에, 차이가 있으면 "기존 컴포넌트 수정 필요" 에, 대응이 없으면 3단계의 판단 규칙으로 "추가 컴포넌트" 인지 페이지 본문인지 가른다.

4. 승격 후보 뽑기
   추가 컴포넌트 중 다른 화면에도 보이는 것을 "공용 승격 후보" 에 올린다. 예: 헤더, 푸터.

5. 사용자 확인
   "기존 컴포넌트 수정 필요" 와 "공용 승격 후보" 는 AskUser 로 하나씩 묻는다. 정해진 것은 반영하고, 정하지 않은 것은 그대로 둔다.

6. 파일 쓰기
   `docs/pages/{라우트 이름}/components.md` 로 쓴다.

### 종료 조건

- [ ] 화면의 모든 요소가 공용 컴포넌트 사용 · 추가 컴포넌트 · 페이지 본문 중 한 곳에 있다
- [ ] 추가 컴포넌트마다 위치와 props 초안이 있다
- [ ] `docs/pages/{라우트 이름}/components.md` 가 위 형식으로 저장되었다

아래 상황이면 AskUser 로 상황을 브리핑하고 정보를 구하세요.
- 공용 컴포넌트와 디자인이 props 로 해결되지 않게 다르다
- 공용으로 올릴 후보가 있다
- 같은 화면의 안이 여러 개이고 확정 표시가 없다
