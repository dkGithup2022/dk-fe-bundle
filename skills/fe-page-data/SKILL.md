# 페이지 데이터 정리

> 산출물(`docs/`, `src/` 아래 파일)은 플러그인 폴더가 아니라 **현재 작업 중인 프로젝트** 아래에 만든다. 스킬 본문의 경로는 모두 그 프로젝트 기준이다.

## 에이전틱 동작

이 동작은 에이전틱한 동작입니다. 아래 순서에 맞게 실행하되, 수행 계획과 종료 조건을 고려하여 여러 번 수행해 결과를 도출해도 됩니다.

### 목적

페이지 하나에 속하는 데이터 정보만 분류해서 스펙을 포함해 나열하는 것이 목적입니다. 페이지가 어떤 데이터를 읽고 쓰는지, 그것이 공용 스펙에 이미 있는지, 페이지 안에서만 쓰는 것인지 가른 뒤 핸드오프 문서로 남깁니다. 코드 파일은 만들지 않습니다. 사용자가 문서를 고친 뒤 다음 스킬이 파일을 만듭니다.

### 입력 & 출력

입력:
- 페이지 디자인. 그 페이지에 속하는 화면 이미지 파일들. 인자로 받거나 대화에서 추론한다.
- 데이터 스펙 문서. `docs/data-spec*.md` (가장 높은 판) 와 `src/types/data/` 의 타입 파일.
- `src/types/api/` 의 현재 파일.
- 기존 코드가 있으면 그 라우트 폴더 (`src/app/{route}/`).
- 대화에서 사용자가 정한 사항.

출력:
- `docs/pages/{라우트 이름}/data.md`: 이 페이지의 데이터 목록. 아래 형식. 각 절의 "위치" 열이 다음 스킬이 파일을 만들 자리다.
  - API 요청 · 응답 모양 → `src/types/api/{domain}.ts`
  - 페이지 전용 데이터 → `src/app/{route}/{이름}.types.ts`
  - 공용 도메인 · 기능 데이터는 위치만 가리킨다. 없으면 "스펙 부족" 으로 적고 데이터 스킬로 돌린다.

```markdown
# {라우트 이름} 데이터

화면: {파일명}, {파일명}
작성: {날짜}
상태: 사용자 검수 전. 이 파일을 고친 뒤 다음 스킬이 파일을 만든다.

## 공용 데이터 (스펙 그대로 사용)

| 항목 | 위치 | 쓰는 필드 | 쓰는 영역 |
|---|---|---|---|
| {도메인 이름} | src/types/data/domain/{name}.ts | {field}, {field} | {화면 영역} |
| {기능 데이터 이름} | src/types/data/feature/{name}.ts | {field} | {화면 영역} |

## 스펙 부족

화면에는 있는데 공용 스펙에 없는 것. fe-extract-data-spec 으로 돌아가 채운다.

| 항목 | 없는 필드 | 근거 |
|---|---|---|
| {도메인 이름} | {field}: {타입} | {파일명} "{화면 문구}" |

## API 데이터

서버와 주고받는 모양이 도메인과 다른 것. 목록 응답, 요청 파라미터, 부분 응답.

| 이름 | 위치 | 필드 | 용도 |
|---|---|---|---|
| {Name}Params | src/types/api/{domain}.ts | {field}: {타입} | {어느 동작의 요청} |
| {Name}Response | src/types/api/{domain}.ts | {field}: {타입} | {어느 영역의 응답} |

## 페이지 전용 데이터

이 페이지 안에서만 존재하는 것. 폼 입력값, 필터 · 탭 선택, 화면 조합용 모양.

| 이름 | 위치 | 필드 | 용도 |
|---|---|---|---|
| {Name} | src/app/{route}/{name}.types.ts | {field}: {타입} | {용도} |

## 애매한 것 (사용자 판단 필요)

| 이름 | 후보 | 이유 |
|---|---|---|
| {이름} | 공용 도메인 / API 데이터 / 페이지 전용 | {한 줄} |
```

```ts
// src/types/api/{domain}.ts
import type { PaginatedResponse, PaginationParams } from "./common";
import type { {Name} } from "@/types/data/domain/{name}";

/** {어느 페이지}의 {어느 동작} 요청 — {파일명} */
export interface {Name}ListParams extends PaginationParams {
  {field}?: {타입}; // {파일명} "{화면 문구}"
}

/** {어느 페이지}의 {어느 영역} 응답 */
export type {Name}ListResponse = PaginatedResponse<{Name}>;
```

```ts
// src/app/{route}/{name}.types.ts
/** {라우트 이름} 페이지 전용. 다른 페이지에서 import 하지 않는다 — {파일명} */
export interface {Name}Filter {
  {field}: {타입}; // {파일명} "{화면 문구}"
}
```

### 분류 규칙

데이터 하나를 놓고 순서대로 묻는다.

1. `docs/data-spec*.md` 또는 `src/types/data/` 에 같은 것이 있는가?
   → 공용 데이터. 그대로 쓴다. 필드가 모자라면 "스펙 부족".
2. 서버에서 받거나 서버로 보내는데 도메인 모양이 아닌가? (목록 · 페이지네이션 · 요청 파라미터 · 필드 일부만 온 응답)
   → API 데이터. `src/types/api/{domain}.ts`.
3. 이 페이지 안에서만 있고 서버와 주고받지 않는가? (입력 중인 폼 값, 고른 탭 · 필터 · 정렬, 여러 도메인을 화면용으로 합친 모양)
   → 페이지 전용 데이터. `src/app/{route}/{name}.types.ts`.
4. 어느 것도 확실하지 않으면 "애매한 것" 에 올린다.

데이터는 가능하면 별도 파일로 둔다. 컴포넌트 파일 안에 타입을 두지 않는다.

### 권장 동작 순서

1. 화면과 기존 코드 읽기
   페이지의 화면 이미지를 전부 본다. 화면을 영역(상단 · 목록 · 시트 등)으로 나누고 영역마다 보이는 정보와 입력을 적는다. 기존 코드가 있으면 이미 쓰는 타입을 적는다.

2. 스펙 읽기
   `docs/data-spec*.md` 와 `src/types/data/` 에서 이 페이지와 관련된 항목과 필드를 뽑는다. `src/types/api/` 에 이미 있는 것도 뽑는다.

3. 필요한 데이터 나열
   1단계의 정보 하나하나를 어느 항목의 어느 필드에서 오는지 적는다. 대응이 없는 것은 따로 모은다.

4. 분류
   분류 규칙대로 네 절에 나눠 넣는다. 억지로 정하지 않는다.

5. 파일 쓰기
   `docs/pages/{라우트 이름}/data.md` 로 쓰고 보여준다. "애매한 것" 과 "스펙 부족" 은 억지로 정하지 않고 그대로 남긴다. 사용자가 이 자리에서 정한 것은 반영한다.

### 종료 조건

- [ ] 화면에 보이는 정보와 입력이 전부 다섯 절 중 한 곳에 있다
- [ ] `docs/pages/{라우트 이름}/data.md` 가 위 형식으로 저장되었다

아래 상황이면 AskUser 로 상황을 브리핑하고 정보를 구하세요.
- 기존 코드의 타입이 스펙과 달라 어느 쪽이 맞는지 알 수 없다
- 같은 화면의 안이 여러 개이고 확정 표시가 없다
